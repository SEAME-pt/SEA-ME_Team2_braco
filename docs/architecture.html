braco architecture

How the braco software is split into ROS 2 packages, which process owns what, how the pieces talk to each other on the real arm (Jetson Nano) and in simulation (PC), where each file lives, how the system is started and what it costs on the Jetson. This page describes what is implemented today. The same content in Markdown: architecture.md; both files are kept in sync.

Last checked against the code: 2026-10-26 Started as issue #30 ADR-0001 · ADR-0002 · ADR-0003

This page follows the code. Every pull request that changes a node, a topic, a service, a parameter, a package, a folder, a make command or the deployment updates the matching section here in the same PR (the map is in section 13), and moves the item in the status between pending, differs and done. If the code and this page disagree, the code wins and this page is the bug.

Principles

One owner per device. arm_driver is the only process that opens the myCobot 280 serial port (/dev/ttyTHS1, 1 Mbaud). Everyone else reaches the arm through its topics and services, so each client can start, stop or crash without touching the port. The page has no direct serial mode. Likewise camera is the only process that opens the eye-in-hand USB camera; the page (and later vision) subscribes to its frames.
The driver never moves the arm by itself. Starting or stopping the system does not zero, park or power on the arm; those are explicit commands (make zero, make park, make down PARK=1). The one automatic move is the park on overheat, run by temperature_monitor (ADR-0003).
Safety lives next to the hardware. Joint limits, the table margin, the watchdog, rest mode and the control owner are enforced in arm_driver, not in its clients: a buggy client cannot bypass them.
Faults are visible. arm_driver is not respawned: if it dies the launch shuts down, arm_routine.sh ends and the container stops. temperature_monitor, joystick_teleop and camera are respawned; the arm never depends on the camera, whose node waits for it when it is unplugged.
One client moves the arm at a time. The page, the joystick, zero/park and the mission take the control from arm_driver before moving; motion from anyone else is ignored, STOP never is (ADR-0002).
One source for each fact. The thermal level is computed once, by temperature_monitor, and published on /diagnostics; the page shows it and does not recompute it. The control owner is kept once, by arm_driver.
Same interface for real and simulated. Everything above the hardware abstraction uses /joint_states, braco_interfaces and the FollowJointTrajectory action, with the same topic, frame and action names on both, so the mission and planning layers cannot tell the simulation from the real arm and run unchanged on both (#37). Only the hardware abstraction layer changes with sim:=true|false.
Every node that moves the arm is a lifecycle node (target, not yet implemented). arm_driver opens the serial port on configure, accepts motion only while active, and deactivate cuts actuation (#6). The same holds for the other nodes that command motion, so the e-stop can force them all out of active (#14). Today every node is a plain node; see section 12.
Logic without ROS where possible. Serial protocol, joystick, LCD and teleop logic live in mycobot_cpp (ros2_ws/src/mycobot_cpp); the control owner and the auto-rest decision are plain headers in braco_driver/include. All unit-tested without a ROS graph.

Scenarios

An operator moves the arm from the page

  1. The user takes the control on the page. With ARM_SOURCE=ros the page lease calls take_control("web").
  2. arm_driver publishes /arm/control_owner = web. The joystick sees it and dims its LED.
  3. The page streams ALL_ANGLES a few degrees ahead of the real angle, only while /joint_states is fresh.
  4. If the page dies, the watchdog stops the arm within 300 ms. After 5 s without motion the owner goes back to free.

Someone picks up the joystick

  1. With the control free, the first stick / X / A / B move calls take_control("joystick").
  2. If the page has the control, the joystick forces it by holding button 8 for 1 s: whoever stands next to the arm has priority.
  3. arm_driver changes the owner, drops the page's pending motion and stops the arm. The page shows "joystick in control"; taking the control from the page fails with 409 until it is free again.
  4. The joystick calls power_on on connect only once it has the control.

A servo gets hot

  1. arm_driver publishes /arm/servo_temperatures (and /arm/servo_voltages) every 2 s, also in rest mode.
  2. temperature_monitor classifies normal (up to 54 °C), warm (55–64 °C) or hot (65 °C or more), publishes /diagnostics and shows it on the LCD.
  3. At hot, once per hot episode, it runs park (park_on_hot): the arm folds, the joints are released so the servos cool, and the arm ends in rest mode, also when park fails. The episode ends only when every joint is below 60 °C (hysteresis), so a reading that jitters around 65 °C does not park the arm again. With park_on_hot: false it only calls set_read_only(true). In rest mode arm_driver drops the pending motion and refuses motion, gripper and power on, but keeps reading.
  4. The page shows the level from /diagnostics. When the arm has cooled down, someone runs make resume (arm-rest-mode.md).

command

Latest wins

ArmCommand carries STOP, JOINTS (one target per joint) or ALL_ANGLES (six angles, one speed). The newest command replaces any pending one, so a slow serial link never builds a queue. Clients stream short moves a few degrees ahead of the angle they read on /joint_states, and only while that feedback is fresh: if the client dies, the arm coasts very little.

safety

Watchdog and limits

When motion commands stop for command_timeout_ms (300 ms), arm_driver stops the arm. Angles are clamped to JOINT_LIMITS (mycobot.hpp); poses that put the wrist or tool below the table margin are refused.

rest

Rest mode

/arm/set_read_only true: motion, gripper and power on are refused; angles and temperatures keep being published. temperature_monitor enters it by itself when a servo reaches 65 °C, once per hot episode (which ends below 60 °C), after parking the arm (park_on_hot); leaving it is manual (make resume). See arm-rest-mode.md and ADR-0003.

Deployment

  • Heavy work stays on the PC. move_group needs 300–600 MB and a full core while planning, so MoveIt 2 and the mission run on the PC and reach the arm on the Jetson through DDS. The Jetson runs only the nodes that need its devices.
  • make up starts the system container; arm_routine.sh runs the launch and the web page side by side, stops both on docker stop, and ends the container when the launch ends.
  • The page's arm source: ARM_SOURCE=ros (real), ARM_SOURCE=gazebo (sim, PC only) or ARM_MOCK=1 (make web, no arm, no ROS, no Docker). There is no mode that opens the serial port.
  • Gazebo's own transport stays on the machine: compose.yml sets GZ_IP=127.0.0.1 (override in .env). With the host network it otherwise picks an interface by itself and, behind a VPN or a firewall, its processes never find each other. ROS 2 (DDS) is not affected. Run a simulation on its own ROS_DOMAIN_ID (e.g. 77) when the real arm is on the network: both publish /joint_states.

Make commands

One command turns the system on
make up

On the Jetson it starts the real arm (driver, temperature, joystick, page); on the PC the simulation and the page. It can be repeated: each step (.env, checks, image, build) is skipped when it is already done, so make up after a code change only rebuilds what changed. No step moves the arm. make alone lists every command; the machine (ROLE=pc|jetson) comes from COMPOSE_PROFILES in docker/.env or is detected (arm64 + Tegra = Jetson).

Build without running out of RAM

On the Jetson: one package at a time, MAKEFLAGS=-j2, Release without tests. make doctor warns without swap and suggests a 4 GB swapfile. Or build on the PC with make jetson-image.

Simulation and the planned upper layers

  • braco_description holds the URDF; its joint limits must match JOINT_LIMITS in mycobot.hpp, and its joint names are the ones on /joint_states (joint1..joint6) on both the real arm and the simulation.
  • sim:=true will start Gazebo with that model, publishing the same /joint_states. Until then braco_description's gazebo.launch.py shows it in Gazebo with gz_ros2_control (/arm_controller, FollowJointTrajectory), and scripts/braco_arm.py runs the same moves there and, with --real, on the arm.
  • How MoveIt's trajectories reach arm_driver on the real arm is decided with #37 and #40.

Status against the target architecture

The target was agreed before the ROS 2 migration: single serial owner, one control owner, one thermal authority, the braco_* layout, one make up. This is where the gap between that target and the code is tracked; update it in the PR that closes or opens a gap.

Done

One control owner. ArmCommand.source, TakeControl.srv, latched /arm/control_owner; motion only from the owner, STOP from anyone (ADR-0002).
Clients follow the owner. Page lease = control web; joystick takes it free or forced (button 8 for 1 s), power_on only as owner; zero/park force and release.

One Makefile. Split in mk/, idempotent make up, ~30 public commands.
Lean repository root. docker, docs, mk, ros2_ws, scripts (operator scripts run by make), web and the Makefile (plus the formatter configs and requirements-dev.txt); mycobot_cpp in ros2_ws/src (one colcon base path, no extra mount); tests/, playground/ and the root requirements.txt removed.

Changing the architecture

Adding a package

  1. Name it braco_<role> and put it in ros2_ws/src. Code with no ROS dependency goes in mycobot_cpp.
  2. package.xml format 3, Apache-2.0, maintainer set; ament_lint_auto as a test dependency.
  3. A README.md with what it does, its topics/services/parameters and how to run it by hand.
  4. Needed on the real arm? exec_depend of braco_bringup, started from braco.launch.py under sim:=false. Simulation or planning only? Keep it out of braco_bringup.
  5. New message or service? In braco_interfaces, never in the package that uses it.
